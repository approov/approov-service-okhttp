# Changelog

All notable changes to this package will be documented in this file.

The format is based on Keep a Changelog and this project adheres to Semantic Versioning.

## [3.8.0] - Unreleased

This release targets the Approov SDK 3.8.0. It is the 3.8.x line; the 3.5.x line keeps its current behaviour. By default a request makes the same token decisions and throws the same exceptions as in 3.5.x (a secure string substitution now mirrors the token decision); always proceeding is opt-in with `ApproovServiceMutator.ALWAYS_PROCEED`, and message signing is a single call. Both become the default, and signing compulsory, in 4.0.0. `initialize` follows the 3.8.0 contract and never resets configuration. Source changes are needed for the moved `io.approov.util.*` packages, for apps that installed `ApproovDefaultMessageSigning` as a mutator, and for the renamed and removed methods (see Changed and Removed).

### Changed
- **`initialize` follows the 3.8.0 contract (SPECIFICATION 5.7).** Every non-empty account ID is forwarded to the Approov SDK with the comment exactly as passed (`null` stays `null`), and the SDK judges repeat calls: the package no longer stores or compares the account ID. The SDK's "already initialized" answer for the same account ID and comment is success and `initialize` returns at once, so every caller in the process may call it. Any SDK exception (`IllegalStateException` for a different account ID or comment, `IllegalArgumentException` for an account ID that did not reach the app intact) is thrown unchanged to the caller, with the package state unchanged; the package raises no rejection of its own. An empty account ID after protection is enabled is ignored and not forwarded; a non-empty one after bypass mode is forwarded and enables protection when the SDK accepts it. `initialize` also rejects a null context with `IllegalArgumentException`.
- **`initialize` never resets configuration.** Token, trace and status headers, the token prefix, the binding header, substitutions, exclusions, the service mutator, the message signing switch and host factories, the stale protection refresh period and the `OkHttpClient` builders keep the values set before or after it. Previously every successful `initialize` reset them all, including after a same account ID reinitialization, and the configuration methods called before the first `initialize` were silently ignored; `getSubstitutionHeaders`, `getSubstitutionQueryParams` and `getExclusionURLRegexs` threw `IllegalStateException` before it. They now take effect and answer at any time. `initialize` no longer clears the ARC returned by `getLastARC()`, and sets the SDK user property only when it first enables protection.
- **Requests before `initialize` and in bypass mode pass through untouched (SPECIFICATION 5.7(f)).** `getOkHttpClient()` may be called before `initialize`; it threw `IllegalStateException("getOkHttpClient: SDK not initialized")`. Every client carries the Approov interceptors, which decide per request: while Approov protection is not enabled a request goes out with no token, trace, status or signature headers, no substitutions and no Approov pinning, only OS trust, and makes no SDK call, even when another caller initialized the SDK and it holds pins for the host. It is neither failed nor held. A client obtained before `initialize`, or in bypass mode, protects its requests once `initialize` enables protection; previously a client built in bypass mode stayed a plain client.
- **Methods that call the SDK are guarded on protection.** `setDevKey`, `precheck`, `getDeviceID`, `setDataHashInToken`, `fetchToken`, `getMessageSignature`, `getAccountMessageSignature`, `getInstallMessageSignature`, `fetchSecureString`, `fetchCustomJWT` and `setInstallAttributes` throw `ApproovException` with the message `<method>: Approov protection not enabled`, without calling the SDK, before `initialize` and in bypass mode. The message was `<method>: SDK not initialized`. `ApproovException` is a checked exception (an `IOException`) and every guarded method declares it. The request path never throws for this reason.
- **Request decisions: `DEFAULT` is `CLOSE_FAILURE` in 3.8.0, `ALWAYS_PROCEED` is opt-in.** `ApproovServiceMutator` names three decision sets. `CLOSE_FAILURE` keeps the 3.5.x interceptor decisions exactly, and they are also the interface defaults: a token fetch proceeds on `SUCCESS` and on `NO_APPROOV_SERVICE` (with an empty `Approov-Token` header), `UNKNOWN_URL` and `UNPROTECTED_URL` send the request with no Approov headers, `NO_NETWORK`, `POOR_NETWORK` and `UNTRUSTED_NETWORK` throw `ApproovNetworkException`, and every other status throws `ApproovFetchStatusException`, `REJECTED` included. A secure string substitution (header or query parameter) mirrors the token decision for the same status (SPECIFICATION 6.2, changed 2026-10-04): it is made on `SUCCESS`; on `UNKNOWN_KEY`, `REJECTED` and `NO_APPROOV_SERVICE` the placeholder is left and the request proceeds, where 3.5.x threw `ApproovRejectionException` for `REJECTED` and `ApproovFetchStatusException` for `NO_APPROOV_SERVICE`, so the backend rather than the device is the enforcement point; the network statuses throw `ApproovNetworkException` and every other status `ApproovFetchStatusException`. `ALWAYS_PROCEED` never aborts: a failed token fetch sends the request with an empty `Approov-Token` header and the reason in `Approov-Status`, and a failed substitution leaves the placeholder in place, for the backend to decide. `DEFAULT`, the out-of-the-box mutator also reinstated by `setServiceMutator(null)`, is `CLOSE_FAILURE` in 3.8.0 and becomes `ALWAYS_PROCEED` in 4.0.0; name one of the two explicitly to keep your decisions fixed across 4.0.0. The interceptor hooks declare `IOException` (including `handlePinningShouldProcessRequest`) so that an app's own opt-in abort is a standard network stack exception (`IOException` or a platform subclass), never an Approov specific type; `CLOSE_FAILURE` keeps the 3.5.x Approov exception types so an existing app catches the same exceptions. An existing override that declares `throws ApproovException` and does not call the interface default still compiles; one that delegates to it (`ApproovServiceMutator.super.handleInterceptorFetchTokenResult(...)`) must widen its declaration to `IOException` or catch it.
- **Message signing is a switch, off by default in 3.8.0.** It is no longer a service mutator: `ApproovService.enableMessageSigning()` switches it on with both the install (`ecdsa-p256-sha256`, member `install`) and the account (`hmac-sha256`, member `account`) signatures, emitted as two members of the same `Signature` and `Signature-Input` dictionaries over the same covered components; `enableMessageSigning(factory)` and `putMessageSigningHostFactory(host, factory)` choose what is signed, for all hosts or per host; `disableMessageSigning()` and `isMessageSigningEnabled()` complete the switch. Signing runs after the mutator's decisions, the substitutions and its `handleInterceptorProcessedRequest` callback, so it covers what is sent, and works the same under every mutator; `setServiceMutator` never switches it on or off, and `initialize` leaves it and the host factories as they are. A signature that cannot be produced is omitted and the request proceeds with the other, or unsigned. From 4.0.0 signing is on and compulsory. **API break:** `ApproovDefaultMessageSigning` no longer implements `ApproovServiceMutator` and has no public constructor, `setDefaultFactory`, `putHostFactory`, `handleInterceptorProcessedRequest` or `supportsProtectionRefresh`; a 3.5.x app that called `setServiceMutator(new ApproovDefaultMessageSigning().setDefaultFactory(factory))` replaces it with `ApproovService.enableMessageSigning(factory)`. Keeping the old form as a deprecated path would have meant a mutator that signs, or a `setServiceMutator` call that toggles signing, which the 3.8.0 contract rules out. `ApproovDefaultMessageSigning.OkHttpComponentProvider` is now public, so a `SignatureParametersFactory` subclass can override `buildSignatureParameters` from any package.
- **Package moves (API break).** The vendored RFC 8941 and RFC 9421 classes moved from `io.approov.util.http.sfv` and `io.approov.util.sig` to `io.approov.util.okhttp.http.sfv` and `io.approov.util.okhttp.sig`. Every Approov Android layer shipped the same class names, so two layers in one app (for example OkHttp and a hybrid framework bridge) failed R8 with duplicate classes; each layer now uses its own prefix. An app that imports `SignatureParameters` or `ComponentProvider` changes the import.
- **BouncyCastle removed; Google Tink, bundled and relocated.** The install signature is converted from DER to the raw `r||s` form with Tink's `EllipticCurves.ecdsaDer2Ieee`, as in `approov-service-android`, and accepted only if re-encoding the result gives back the SDK's bytes exactly, so a malformed or non-canonical signature is left out (and the request proceeds with the other signature or unsigned) rather than misconverted. Tink 1.23.0 and its runtime dependencies (Gson, Error Prone annotations, JSR-305) are bundled in the AAR relocated under `io.approov.util.okhttp`, so they never clash with an app's own copies or another Approov layer, and the published POM lists no new dependency. No consumer rule keeps Tink classes, so R8 removes what is not used (an R8 shrunk consumer keeps only `EllipticCurves`); only Tink's protobuf rule is restated for the relocated package. The release AAR goes from 5.7 MB to 3.4 MB.
- `SignatureParametersFactory` gains `setUseInstallAndAccountMessageSigning()` (the new default of `generateDefaultSignatureParametersFactory()`), `getAlgs()` and `setAddApproovStatusHeader(boolean)`. `setUseInstallMessageSigning()` and `setUseAccountMessageSigning()` now select a single signature, and a bare `new SignatureParametersFactory()` produces both signatures unless one is selected. The factory no longer sets `alg` on the built `SignatureParameters`; a subclass that does set one produces that single signature (backwards compatible).
- `MITM_DETECTED` is gone from the Approov channel. The 3.8.0 SDK no longer pins its own attestation channel (an additional encryption layer replaces it), so an intercepting proxy on the attestation path no longer blocks a token fetch, and `Approov.TokenFetchStatus.MITM_DETECTED` is replaced by `UNTRUSTED_NETWORK` (a fundamental TLS trust failure). This layer classifies `UNTRUSTED_NETWORK` as a network failure alongside `NO_NETWORK` and `POOR_NETWORK` (`ApproovServiceMutator.isNetworkFailure`). Pinning of the integrator's own API domains is unchanged and a pin mismatch there still fails the connection.
- Header configuration uses the common service layer names: `setTokenHeader(header, prefix)`, `getTokenHeader()`, `getTokenPrefix()`, `setTraceIDHeader(header)`, `getTraceIDHeader()`. The okhttp-specific `setApproovHeader`, `setApproovTraceIDHeader`, `getApproovTokenHeader`, `getApproovTokenPrefix` and `getApproovTraceIDHeader` remain as deprecated aliases.
- `ApproovPinningInterceptor` reports a cleartext (non-TLS) connection to a pinned host with `javax.net.ssl.SSLPeerUnverifiedException`, the same network stack exception as a pin mismatch, instead of the Approov-specific `ApproovNetworkException`; a cleartext connection to a host with no pins is no longer blocked by this layer. The interceptor also rebuilds its pins on first use if none were available when it was constructed, since the 3.8.0 SDK only holds pins once a token has been fetched for the installation.

### Added
- `ApproovServiceMutator.CLOSE_FAILURE` and `ApproovServiceMutator.ALWAYS_PROCEED` (see Changed); `ApproovServiceMutator.DEFAULT` now refers to `CLOSE_FAILURE`.
- `ApproovService.enableMessageSigning()`, `enableMessageSigning(SignatureParametersFactory)`, `disableMessageSigning()`, `isMessageSigningEnabled()` and `putMessageSigningHostFactory(host, factory)` (see Changed).
- **`Approov-Status` header** (`setStatusHeader(header)`, `getStatusHeader()`), on by default, carrying the SDK token fetch status in lowercase (`success`, `no_network`, `untrusted_network`, `no_approov_service`, `rejected`, ...) on **every** request processed by Approov, successful ones included, and identical on Android and iOS. It tells the backend why a particular request carries no attestation proof, to log against the request and act on. Not sent to domains that are not protected by Approov. `setStatusHeader(null)` disables it. Failure information is never placed in the token header. `ApproovRequestMutations.getStatusHeaderKey()` exposes it to mutators, and message signing covers it so the reported status cannot be stripped or altered without invalidating the signature.
- Tests for the 3.8.0 contract: `DEFAULT` is `CLOSE_FAILURE`, and every `CLOSE_FAILURE` token and substitution decision throws the 3.5.x exception type with nothing sent; under `ALWAYS_PROCEED` every failure status proceeds with an empty token header and the lowercased status on the status header and no substitution aborts; a successful request reports `success`; the status header can be renamed and disabled; a guard on the out-of-the-box signing state (off until `enableMessageSigning()`, then both signatures, under every mutator, never toggled by `setServiceMutator` or `initialize`); one signature falls back to the other when a key is unavailable; a custom mutator can still suppress all headers or fail closed by throwing; the DER to raw conversion against shared golden vectors and malformed DER.
- `verifyReleaseAar` and `verifyPublishedPom` build checks, run in CI and before a Maven release: the AAR must contain no BouncyCastle, no unrelocated Tink, Gson, Error Prone or JSR-305 class, none of the old shared `io.approov.util.http.sfv` / `io.approov.util.sig` classes and nothing outside this layer's packages, and the published POM must list none of those libraries.
- `isApproovServiceEnabled()`: true once any `initialize` has succeeded, bypass mode included (replaces `isInitialized()`). `isApproovProtectionEnabled()`: true once the Approov SDK is initialized and requests are protected (replaces `isApproovEnabled()`).
- `setInstallAttributes(String) throws ApproovException`, replacing `setInstallAttrsInToken` (TESTING_REQUIREMENTS 7). It still passes the signed JWT to the SDK's `Approov.setInstallAttrsInToken`.
- Tests for the initialize contract (forwarding verbatim, repeats, SDK rejections propagated unchanged with state untouched, configuration never reset, bypass upgrades), for requests before `initialize` and in bypass mode over a local HTTPS server (unprocessed, no SDK call, no Approov pinning even with the SDK initialized elsewhere and holding a wrong pin), for every guarded method (exact message, no SDK call, checked exception declared), for the status carried by direct method exceptions, and for the absence of a layer prefetch. SDK calls go through a package-private `ApproovSdkFacade`, as in `approov-service-android`, so tests can record them; it is not public API.

### Removed
- `isInitialized()` and `isApproovEnabled()`, with no alias (SPECIFICATION 5.2, 5.7(c)): use `isApproovServiceEnabled()` and `isApproovProtectionEnabled()`.
- `setProceedOnNetworkFail(boolean)` and `getProceedOnNetworkFail()`, with no alias (SPECIFICATION 5.2, changed 2026-10-04). A decision on `NO_NETWORK`, `POOR_NETWORK` and `UNTRUSTED_NETWORK` belongs to the service mutator: `CLOSE_FAILURE` always throws `ApproovNetworkException` for them, on the token fetch and on secure string substitutions, and an app that wants such a request to proceed installs `ApproovServiceMutator.ALWAYS_PROCEED` or its own mutator.
- `prefetch()`, with no alias (SPECIFICATION 5.2, changed 2026-10-04): the platform SDK manages prefetching and the package starts no fetch of its own. `getLastARC()` makes no SDK call; a direct method whose SDK call throws now clears the ARC it reports, since that fetch carried none.
- `setInstallAttrsInToken(String)`, renamed `setInstallAttributes(String)` with no alias.
- `setUseApproovStatusIfNoToken` / `getUseApproovStatusIfNoToken`: the fetch status is reported on `Approov-Status`, never in the token header.
- `setApproovInterceptorExtensions` / `getApproovInterceptorExtensions` and the `ApproovInterceptorExtensions` interface: use `setServiceMutator` / `getServiceMutator` with an `ApproovServiceMutator`.
- `ApproovDefaultMessageSigning.processedRequest(request, changes)` (deprecated): the implementation is `handleInterceptorProcessedRequest`.
- The BouncyCastle dependency (`bcprov-jdk15to18`, bundled relocated under `io.approov.internal.okhttp.bouncycastle`).
- `USAGE.md` is replaced by `ADVANCED.md`, since the standard integration needs none of it. The documentation now calls this the Approov Package for OkHttp: integrating the package is integrating Approov, and the wrapped SDK is a detail. The initialization string is called the Approov account ID (what the CLI and SDK call the config string), with the README saying where to get it and that it is not a secret.

### Fixed
- **A signing configuration error no longer crashes an app that enqueues its calls (SPECIFICATION 1.6, 1.7(a)).** `ApproovDefaultMessageSigning.RequiredBodyDigestException`, thrown when a body digest configured as required (`setBodyDigestConfig(alg, true)`) cannot be generated, for example for a `GET` or a one-shot body, was an `IllegalStateException`. OkHttp delivers an `IOException` "canceled due to" to `onFailure` for such an exception and then rethrows it on its dispatcher thread, which terminated the app process (measured on 3.5.8). It is now an `ApproovException`, and so an `IOException`, with the same name: it still fails every such request immediately, `execute()` throws it and an enqueued call receives it in `onFailure` with nothing rethrown. An unsupported signature algorithm now fails the request with an `ApproovException` instead of an `IllegalStateException`. **Source change:** `RequiredBodyDigestException` is a checked exception, so a `SignatureParametersFactory` subclass whose `buildSignatureParameters` override calls `super.buildSignatureParameters` declares `throws RequiredBodyDigestException` (or handles it), and code that caught it as an `IllegalStateException` catches it as an `IOException`.
- **Message signing signs the URL exactly as OkHttp sends it (SPECIFICATION 3.3).** `@target-uri` was taken from `HttpUrl.uri()`, the `java.net.URI` form, which re-encodes characters OkHttp sends raw in a query (`|` became `%7C`, and `{`, `}`, `^` and a backtick were encoded too), so the backend, which rebuilds the value from the request it receives, could not verify either signature for such a URL, for example a maps or search API query like `path=color:red|weight:5`. `@target-uri` is now `HttpUrl.toString()` without the fragment, which is never sent, and the request URL is no longer parsed with `java.net.URI` anywhere on the signing path. The other derived components follow RFC 9421 section 2.2 from the same URL: `@authority` carries the port when it is not the scheme's default (it was the host alone) and brackets an IPv6 address, `@query` starts with `?` and is `?` alone when there is no query (it had no `?`, and a request with no query went out unsigned), `@request-target` comes from the path and query as sent, and `@query-param` looks the parameter up by its encoded name and signs its value percent-encoded again (it signed the decoded value). A host factory is still chosen by the host alone, without the port. Tests send URLs with `|`, `%20`, a literal `%25`, a non-ASCII character and characters `java.net.URI` rejects, synchronously, enqueued and through a redirect, and verify both signatures against a signature base rebuilt only from what the server received.
- **Rebuilt attempts are reprotected.** A network attempt whose URL, method or headers differ from the request the protection was applied to was rebuilt by OkHttp or by the app: a redirect (a `303` also changes the method), or an `Authenticator` retrying a `401` with a new `Authorization`. Such an attempt is stripped of the previous protection and protected afresh, so its signature covers what is actually sent; previously an authenticator retry carried a signature computed over the old `Authorization` and was rejected by the backend. The network layer now strips the protection applied to the original destination (token, trace and status headers, signatures, and the secure string substitutions, whose placeholders are restored) and applies protection afresh for the redirect target: a redirect to a domain Approov does not protect leaves with no Approov headers at all, and a redirect within a protected domain is re-signed over its new target URI and method. Previously the original destination's headers, including substituted secrets, travelled with the redirect, and a `303` to the same URL kept a signature computed over the original method.
- **A refresh that finds the URL no longer protected strips the protection** instead of sending the previous token, status and signatures unchanged. Stripping restores every original field of a substituted header, in order, and only when the header still holds the value this layer installed, so a value the app changed between attempts (for example from an OkHttp `Authenticator`) is kept and substituted afresh. The comparison uses the value as OkHttp stores it (trimmed), so a secure string with surrounding whitespace is recognised and restored, and the layer keeps only a digest of the installed value, never a second copy of the secret. A substituted query parameter is restored to its placeholder whenever the URL is the one the protection was applied to, whatever else about the attempt changed, so an authenticator retry fetches the secure string afresh.
- **A retry of the original request is refreshed again.** The stale protection refresh used to update the marker shared with the original request, so an OkHttp retry that reuses the original request object was sent with its stale headers under a marker that looked fresh. The refreshed request now carries its own marker and the original keeps the one describing its own headers.
- **No pin verdict cache: every connection check evaluates the current pins for the request's host.** `ApproovPinningInterceptor` cached handshakes that had passed the pin check, keyed by okhttp's `Handshake`, whose equality covers the TLS version, cipher suite and certificate chain but not the host. Two hosts served with the same certificate (a wildcard certificate, or two API domains behind one CDN) therefore shared a verdict, and a host whose own pins did not match was admitted without a check once the other had passed (approov/core-project-approov#723; shipped from 3.4.1). The cache was an optimisation of a cheap check and is removed rather than rekeyed, which also removes the pin generation bookkeeping that kept a verdict reached against rebuilt pins out of it: after a pin rebuild the next request is checked against the new pins.
- The token header name and prefix are read as one snapshot, so a request never combines the header name of one configuration with the prefix of another when `setTokenHeader` is called while requests are in flight. `ApproovRequestMutations.getTokenHeaderPrefix()` exposes the prefix used.
- Combining repeated header field values for message signing keeps the separator after an empty leading value (`["", "value"]` canonicalises to `", value"`), matching RFC 9421 section 2.1; separation is by element rather than by accumulated length.
- The `SignatureParameters` copy constructor now copies the debug mode flag, so `setDebugMode(true)` on a base parameter set takes effect for both signatures and `Signature-Base-Digest` carries one member per signature.
- `getLastARC()` no longer performs a token fetch of its own (it fetched a token for the first pinned domain, which could return the ARC of a later, successful attestation rather than the one behind the request that failed, and cost a network round trip). It now returns the ARC recorded from the most recent fetch performed by this layer, from the interceptor or a direct method, with no network activity. Removes the getLastARC patch implementation tracked in approov/core-project-approov#566.
- A header that is present with an empty value is now a valid covered component for message signing (RFC 9421 §2.1), so a request sent with an empty `Approov-Token` is still signed. Previously the signature base build failed and the request went out unsigned. This is in the shared `ComponentProvider` (now `io.approov.util.okhttp.sig.ComponentProvider`) and applies to every layer carrying a copy of it.
- A custom `ApproovServiceMutator` that decides to substitute a secure string for a result that carries none (it returns `true` for a status other than `SUCCESS`) now leaves the placeholder and the request proceeds, as in `approov-service-android`. Previously a header was sent as the prefix followed by the literal `null`, and a query parameter threw a `NullPointerException` out of the interceptor.
- The pins are rebuilt when a token fetch reports `isForceApplyPins`, as in `approov-service-android`, not only on `isConfigChanged`. Previously a request for the current pins to be applied without a configuration change was ignored, and since the pinning interceptor only rebuilds an empty pinner on its own, a pinner that already held pins kept the stale ones. The pins are rebuilt once when both are set, and `fetchConfig` is still called only for a configuration change.


## [3.5.8] - 2026-07-16

### Added
- Stale protection refresh: a new network interceptor detects requests that were held between Approov protection being applied and actual transmission (for example by a device deep sleep or doze period, or an app-level request queueing/backoff mechanism) and refreshes the Approov token and any message signature immediately before the request is sent, instead of transmitting expired credentials. Since it operates per network attempt it also refreshes protection on OkHttp generated retries and redirect followups. Configurable via `ApproovService.setStaleProtectionRefreshPeriod()` (default 3000ms, `<=0` disables). Because a refresh reinvokes the mutator's `handleInterceptorProcessedRequest` callback, it is gated on the new `ApproovServiceMutator.supportsProtectionRefresh()` capability: the default mutator and `ApproovDefaultMessageSigning` support it, while custom mutator implementations are never reinvoked unless they opt in.
- Service-layer version is now baked into the AAR at build time via `BuildConfig.APPROOV_SERVICE_VERSION` and reported to the Approov SDK via `setUserProperty("approov-service-okhttp/X.Y.Z")` during initialization. Local builds report `dev`.
- Manual `Release to Maven` workflow for publishing an existing release tag from `main`. It validates the requested semantic-version tag, verifies that the tag belongs to `main`, and requires the top CHANGELOG entry to match both on `main` and at the tagged commit before publishing.

### Changed
- Android build migrated from the unmaintained `com.github.johnrengelman.shadow` 8.1.1 plugin to the maintained fork `com.gradleup.shadow` 8.3.11 for Gradle 9 compatibility (Gradle 9 removed `FileCopyDetails.mode`, making the old plugin fail with a `MissingPropertyException`). Shaded BouncyCastle jar verified byte-identical; minimum supported Gradle remains 8.3.
- Publish workflow now passes `-PapproovServiceVersion` to `assembleRelease`, keeping the runtime version in lockstep with the Maven artifact version.
- **Breaking:** the HTTP `Signature` header now encodes install and account signatures as RFC 9421 Structured Fields Byte Sequences (`install=:<base64>:` / `account=:<base64>:`), matching every other Approov service layer. Verifiers that only accept the legacy quoted-String form must be updated.

### Fixed
- **Message-signing fail-open conformance**: a body digest configured as *required* that cannot be generated now fails **closed** (aborting the request) instead of being silently skipped. All other signing failures (signature unavailable, base64 decode, ASN.1/DER decode, account-branch errors) continue to fail **open** (the request proceeds unsigned) but are now logged at **error** level for production visibility. Unsupported signing algorithms still fail closed.
- **Token binding header**: the binding header is now matched case-insensitively (HTTP header names are case-insensitive) and a present-but-empty value is forwarded to the SDK, while an absent header is skipped.
- **Substitution header configuration**: adding and removing secure-string substitution headers now matches names case-insensitively. Re-adding the same logical header replaces its configuration without creating duplicate entries.
- **Binding/substitution conflict**: configuring the same header for both token binding and secure-string substitution now fails fast with `IllegalArgumentException`, preventing a token from being bound to a placeholder that differs from the substituted value sent to the backend.
- **Trace ID header**: an empty trace ID returned by the SDK is now emitted as an empty header value rather than omitted, so the backend has evidence that Approov processing occurred.
- **`NO_APPROOV_SERVICE`**: the request now proceeds emitting an **empty** `Approov-Token` header (and a trace ID if the SDK provides one) as evidence that Approov processing occurred, instead of omitting the headers (root TESTING_REQUIREMENTS §2 Missing Artifacts Fallback). `UNKNOWN_URL`/`UNPROTECTED_URL` still send no headers.
- **REFERENCE.md**: corrected the deprecated `setApproovInterceptorExtensions` signature — its parameter is an `ApproovServiceMutator` (the legacy `ApproovInterceptorExtensions` interface is a deprecated subtype), not `ApproovInterceptorExtensions`.

## [3.5.7] - 2026-04-09

### Added
- Integrated a localized testing framework for comprehensive service layer verification.
- Added extensive test coverage for token management, pinning synchronization, and request mutation scenarios.
- Enhanced internal service components to improve testability.
- Added `ApproovService.isInitialized()` to expose the service-layer initialization state.
- Consumer ProGuard rules (`consumer-rules.pro`) to automatically preserve native SDK interfaces and internal cryptography bounds.

### Changed
- `setProceedOnNetworkFail()` and `getProceedOnNetworkFail()` are now obsolete no-ops. Mutator defaults dynamically enforce exceptions upon network drops.
- Shaded and relocated the BouncyCastle dependency (`io.approov.internal.okhttp.bouncycastle`) to prevent version collisions for consuming applications.
- Removed the transitive `org.bouncycastle:bcprov-jdk18on` dependency from `pom.xml`.
- Simplified `initialize` — removed the service-layer re-initialization guards (same-config short-circuit, `reinit` comment check). The service layer now always resets its own state and forwards non-empty config directly to the platform SDK. The SDK returns `false` if already initialized with the same config (service layer logs and continues), or throws `IllegalStateException` for a different config (service layer re-throws).

### Fixed
- Enforced SDK initialization gating across all public API endpoints (`fetchCustomJWT`, `getDeviceID`, `setDataHashInToken`, `setInstallAttrsInToken`, etc.) to prevent unhandled `IllegalStateException` crashes from the platform SDK when the service layer is operating in bypass/uninitialized mode.
- Prevented premature construction of the `ApproovPinningInterceptor` and immediate `getPins()` calls when the Approov service layer is initialized with an empty configuration string.
- Initializing with an empty config string now keeps the service layer initialized while returning a plain `OkHttpClient` without Approov processing.
- Initializing first with an empty config string and later with a valid non-empty config string now enables Approov at runtime instead of being rejected as a different-config reinitialization.
- `initialize` now explicitly throws `IllegalArgumentException` when `config` is `null`, with a clear message directing callers to pass `""` for bypass mode. Passing `null` previously caused a silent coercion to `""` which masked caller errors.
- The 2-arg `initialize(context, config)` overload now correctly passes `null` (not `""`) as the comment to the native SDK, preventing unexpected re-initialization mismatches on subsequent calls.


## [3.5.6] - 2026-02-11

### Added
- ApproovServiceMutator protocol with default behavior to centralize decision points in the service flow.
- Mutator hooks for precheck, token fetch, secure string fetch, custom JWT fetch, interceptor decisions, and pinning.
- REFERENCE.md & CHANGELOG.md & USAGE.md
- Added `setUseApproovStatusIfNoToken` to allow using status as token value when token is missing.
### Changed
- ApproovService now routes decision logic through the service mutator and exposes set/get APIs.
- Pinning logic is now applied via `ApproovPinningInterceptor` which checks `ApproovServiceMutator.handlePinningShouldProcessRequest`.
